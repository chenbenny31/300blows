## 35. 课程对象发现与失败重试（A17 · 无直接 LC，原型 LC 207 / 210）
**证据：** IC2；用户贴的平台标签；Onsite / OOD coding（P1）
**本文件合同：**
- `prevCourses` 用注入的 `unordered_map<string, vector<string>>` 模拟 `course.prev_courses`；不在 map 里的课程没有先修课。`hasFailed` 是注入的 `std::function<bool(const string&)>`，每次调用代表"尝试一次"。
- 只处理从入口课程沿先修关系可达的课程；不可达课程不会被尝试。入口重复、多处引用同一门课、同一先修在列表中重复出现，都只算一个节点 / 一条边。
- 就绪队列按发现顺序（BFS）初始化，解锁的课程按其被发现的顺序入队；失败的课程放到队尾，等当前已就绪的课程都轮一遍后再试。
- 假设每门课最终会通过（且依赖无环），所以主方法一定结束并返回全部可达课程的成功顺序；若有环，环上及其下游课程永不就绪，不出现在结果里。
- `completionOrderWithLimit`（追问）：每门课最多尝试 `maxAttempts` 次，第 `maxAttempts` 次失败后永久放弃，其下游课程也不会完成，结果只含成功的课程。

**先问面试官：**
- `prev_courses` 是先修课（我依赖它）还是后续课？入口课程本身也要完成吗？
- 失败后什么时候重试：立即重试、放到队尾、还是等一轮？会不会永久失败、有没有重试上限？
- 多门课同时就绪时顺序有要求吗（返回任一合法顺序是否可以）？
- 依赖关系可能有环吗？有环时要报错还是返回部分结果？
- `has_failed` 有副作用 / 很慢吗（是否需要并发、是否每次调用都算一次尝试）？

**思路：** 三步。①发现：从入口 BFS，`seen` 保证每门课只入列一次。②建图：对每门已发现课程，用一个局部 `linked` 集合去重它的先修列表，每个不同的 (先修, 课程) 只建一条边、`waiting` 只加一次，保证"边数 = 后续要减的次数"。③Kahn：取队首，失败就放回队尾（它的 `waiting` 已是 0，不影响别人），成功则记录并让每个下游 `waiting--`，降到 0 入队。每门课只在 `waiting` 恰好降到 0 时入队一次，失败重试只是同一份在队列中循环，所以不会重复记录。

**复杂度：** V = 可达课程数，R = 可达课程先修列表的引用总数（含重复），E = 去重后的边数（E ≤ R），F = 总失败次数。T O(V + R + F) 次哈希操作（字符串哈希另乘平均名长），`hasFailed` 共调用 V + F 次；S O(V + E)。

**Follow-up：**
- 重试上限 / 永久失败（已实现：`completionOrderWithLimit`）：失败计数达到上限后不再入队，下游自然卡住。还可以返回"被阻塞的课程列表"= 已发现但不在结果中的课程。
- 检测环：结束后若 `passed.size() < courses.size()`（主方法、无上限时）说明有环，可返回空或抛错。
- 失败后指数退避 / 等若干轮再试：队列元素改成 `(可尝试的轮次, course)` 并按轮次推进，或用 `priority_queue` 按下次可尝试时间排序。
- 并行尝试（每轮把所有就绪课程同时尝试）：按层处理队列，`sz = ready.size()` 冻结一轮，类似 LC 1136 求学期数。
- 发现阶段的 `prev_courses` 是远程调用：同一课程只调用一次（本写法 `seen` 保证），可缓存其结果复用到建图步骤。

**易错点：**
- 重复引用（`B: [A, A]`、菱形依赖）导致 `waiting` 多加：若下游列表又去重了，`B` 永远等不到 0；若不去重，则同一课程可能被重复入队、重复记录。
- 失败后立即重新尝试（栈式 / 原地重试），违背"稍后重试"的语义，也会让无关课程的顺序变化。
- 失败时又对下游做了 `waiting--`，或成功前就解锁下游。
- 用 `waiting[c]` 的 `operator[]` 读取未发现的课程，意外插入新键；本写法只在已发现的课程上建图。
