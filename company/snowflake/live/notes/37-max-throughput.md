## 37. 串联服务最大吞吐（B11 · 无直接 LC；875 / 2064 答案二分原型）
**证据：** 职级／环节未确认；Hack2Hire 导出（P1）
**本文件合同：**
- `t[i] >= 1`、`c[i] >= 1`（int），`budget >= 0`（long long）；返回 long long。
- 每个服务升级次数默认不限；升级 x 次后吞吐 `t[i] * (x + 1)`，系统吞吐 = 所有服务的最小值。
- 只返回最大吞吐，不返回升级方案；空服务列表返回 0。
- 前提：答案本身放得进 long long；中间的上界和成本计算都按溢出安全写（先除后乘）。
- 附 `maxThroughputCapped`：每个服务最多升级 `cap[i]` 次（cap 用 long long）。

**先问面试官：**
- t、c 都是正整数吗？budget 可以为 0 吗？数值上限多大（决定要不要 long long）？
- 每个服务升级次数有没有上限？
- 吞吐是 `t * (x + 1)` 线性增长，还是别的函数？
- 只要最大吞吐，还是要每个服务的升级次数？

**思路：** 固定目标 T，服务 i 至少需要 `ceil(T / t[i]) - 1 = (T - 1) / t[i]` 次升级，各服务独立，总成本随 T 单调不减，所以 feasible(T) 是单调的（前段 true，后段 false），二分最后一个 true。下界 `min(t)` 零成本可达；上界取 `min_i t[i] * (budget / c[i] + 1)`，即把全部预算给单个服务也到不了更高。成本累加时用 `need > left / c[i]` 判断，避免 `need * c[i]` 溢出。

**复杂度：** 两个方法都是 T O(n log U)，S O(1)；n 为服务数，U 为二分上界（至多约 9.2e18，所以 log U <= 63）。

**Follow-up：**
- 每服务升级次数上限（已实现：`maxThroughputCapped`）：上界里 `most` 取 `min(budget / c[i], cap[i])`，可行性多一条 `need > cap[i]` 就失败。
- 返回升级方案：二分出答案 T 后，再跑一遍 `need_i = (T - 1) / t[i]` 就是每个服务的升级次数，剩余预算可以不花。
- "每次升级当前最慢的服务"（min-heap）：要让最小值上升，最慢的那个必须升级，所以这个贪心结果是对的（升不起就停），但它一次只加一级，总升级次数可达 budget / min(c) ~ 1e9 以上，T O(升级次数 · log n) 太慢。二分是 O(n log U)。不要说成"升级最便宜的"，那是错的（见测试 shared budget）。
- 吞吐不是线性（如 `t * 2^x`）：只要每个服务的所需次数可以单独算出、且随 T 单调，二分框架不变，只改 `need`。

**易错点：**
- 找最后一个 true 时 `mid = lo + (hi - lo) / 2` 再 `lo = mid`，lo、hi 相邻时死循环；要向上取整。
- `need` 写成 `T / t[i]`：T 恰好是 t[i] 的倍数时多算一次升级。
- 上界 `t[i] * (budget / c[i] + 1)` 直接乘会溢出；`most + 1 <= LLONG_MAX / t[i]` 的 `+1` 也会溢出，应写 `most < LLONG_MAX / t[i]`。
- 用 int 累加成本或把 budget 设成 int：1e9 量级的 t 乘以升级次数立刻溢出。
