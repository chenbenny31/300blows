## 40. 动态黑名单整数流过滤（B19 · 无直接 LC；706 集合基础）
**证据：** 职级未确认；平台 Phone Screen（P1）
**本文件合同：**
- `process(x)` 返回 x 是否放行（true = 输出）；每次出现都单独判断，重复输入每次都放行（不去重）。
- `block(x)` / `unblock(x)` 立即生效，影响之后的 `process`；重复 block / unblock 是幂等的。
- follow-up 合同：`block` / `unblock` 返回 true 表示发出状态变化事件，仅当 x 曾在流中出现过，且这次调用真的改变了它的可见性（visible = seen && !blocked）。
- 对从未出现过的值 block / unblock 不发事件，但黑名单照样记录（之后 `process(x)` 被拦）。
- 值为任意 int（含负数）；单线程。若面试只要基础版，`block` / `unblock` 写成 void，去掉 `seen`。

**先问面试官：**
- 重复输入是每次都输出，还是同一个值只输出一次？（材料两种说法都有）
- 解除黑名单后，之前被拦下的那些出现要不要补发？
- 对已出现过的值 block / unblock 时，是否要发"状态变化"事件？对没出现过的值呢？
- 是否有多个生产者 / 并发修改黑名单？

**思路：** 黑名单就是一个 `unordered_set<int>`，`process` 一次查表。事件版多存一个 `seen` 集合：可见性 = 出现过且不在黑名单，不需要第三个集合；`insert(...).second` 与 `erase(...) > 0` 直接告诉我们这次修改有没有改变状态，于是"真改变 && 出现过"就是事件条件，重复修改天然不发事件。

**复杂度：** `process` / `block` / `unblock` 均 T O(1) 平均；S O(B + U)，B 为当前黑名单大小，U 为出现过的不同值个数（只有事件版需要 U）。

**Follow-up：**
- 已出现值的状态变化事件（已实现：`block` / `unblock` 的返回值）：也可以改成回调或往输出队列 push `{x, "hidden"/"visible"}`，判定条件不变。
- 解封后补发被拦下的值：为每个被拦值记录次数 `unordered_map<int,int> held`，unblock 时一次性输出；要先问是否保序（保序需要按到达顺序的队列）。
- `seen` 无限增长：只在需要事件时才存；或限制为最近 N 个值（LRU / 时间窗），超出窗口的值不再发事件，需说明语义变化。
- 并发：读多写少用 `std::shared_mutex`（process 共享锁、block 独占锁）；回调不要在持锁时调用，避免死锁和长临界区。
- 黑名单是区间（如 [100, 200]）：用 `std::map<start,end>` 存不相交区间，`upper_bound` 查询 O(log B)。

**易错点：**
- 用 `blocked[x] = true` 式的 `unordered_map` 并在 `process` 里用 `operator[]` 读，查一次就插入一个 false 项。
- 事件条件只看 `seen`，不看这次修改是否真的改变状态，重复 block 会重复发事件。
- 把"从未出现过就不发事件"写成"不记录黑名单"，导致之后这个值第一次出现时被放行。
- 重复输入只放行第一次（误加去重），与本合同不符；先问清楚。
